# Правила проекта для ИИ-ассистентов

Магазин на Django 6.1, Django REST Framework и PostgreSQL 16. Приложения Django находятся в `backend/`. Фронтенд на React 19 и TypeScript 7 находится в `frontend/`. Для запуска среды разработки
используйте `docker compose up -d`. Для локальных проверок фронтенда установите зависимости командой
`npm ci --prefix frontend` в Node.js 24.

## Бэкенд

- Размещайте бизнес-логику в сервисах или методах моделей. Используйте `transaction.atomic` для
  операций, которые должны выполниться целиком, и `select_for_update` для блокировки строк при
  конкурентных изменениях.
- По умолчанию API требует аутентификации через `IsAuthenticated`. Публичным операциям явно
  задавайте `AllowAny` и сохраняйте ограничения доступа для приватных операций.
- При изменении API обновляйте OpenAPI. Выполняйте
  `docker compose exec web python manage.py spectacular --validate --fail-on-warn`.
- Запускайте тесты командой
  `docker compose exec web python manage.py test --settings=config.settings.test`.

## Фронтенд

- Используйте `react-router` 8 в режиме данных через `createBrowserRouter` и импортируйте
  `RouterProvider` из `react-router/dom`.
- Загружайте серверные данные через TanStack Query v5 с `queryOptions` и объектным синтаксисом
  `useQuery`. Используйте загрузчики маршрутов для предзагрузки в общий кэш.
- Выполняйте запросы через типизированный клиент `api` из `frontend/src/api/client.ts`. Обновляйте
  `frontend/src/api/schema.d.ts` из запущенного Django командой `npm --prefix frontend run api:types`
  и сохраняйте сгенерированный файл в Git.
- Используйте строгие типы без `any`. API передаёт цены десятичными строками. Преобразуйте их в числа
  для форматирования, денежные суммы рассчитывает сервер.
- Перед коммитом в `frontend/` запускайте `npm run typecheck`, `npm run lint` и `npm test`.


## Основа и объём итогового проекта

Это продолжение рабочего магазина из лабораторных №1–10. Исходный срез для плана — коммит
`4773316` ветки `codex/lab10-independent`. При начале работы сверить фактическую ветку и сохранность
изменений лабораторной №10. Критерии сдачи — лабораторная №11, части 2–5, 7 и 9, и требования
владельца проекта. Порядок реализации и приёмки — в [плане для владельца](LAB11-PLAN.md).

- Предметная область — независимый книжный магазин «Книжная полка». Каталог состоит из физических
  изданий, сгруппированных по жанрам. Сохранять общую модель интернет-магазина, сервисы и историю.
- В приложенных материалах нет таблиц лабораторной №0.3. Официальный шифр по имени и фамилии
  неизвестен. Рабочий выбор для согласования на КТ1 — книжный магазин с модулем **М1 «Отзывы и
  рейтинг»** из части 3 лабораторной №11. Если преподаватель подтвердит другой шифр или правило,
  уточнить зачётный вариант и его серверные условия. По требованию владельца реализовать
  **все М1–М4** как функции магазина. Для М2–М4 переиспользовать существующие сервисы и API,
  запланировать только недостающую часть. Условия из отсутствующих пп. 11.2, 11.4 и 11.5
  лабораторной №0.3 требуют отдельной сверки, если преподаватель предоставит задание.
- Объём части 4 — **все Р1–Р14**. Использовать готовое, довести неполное до критерия и реализовать
  недостающее. Отдельные индивидуальные доработки из лабораторной №7 входят в существующую систему.
- Б1 прямо требует `backend/` и `frontend/`. Сначала перенести Django в `backend/` отдельным
  изменением, затем добавлять функции. Обновить пути в Docker, настройках, проверках и этом файле.
  Сохранить имена приложений и миграций, схему БД, прежние данные и внешние URL. Django-шаблоны
  можно сохранить для совместимости. Рабочие сценарии персонала для защиты проходят в React.

## Целевая архитектура и контракты

### Книги и данные

- Одна карточка `Product` представляет конкретное издание, SKU остаётся стабильным. Добавить
  типизированные книжные метаданные (например, отдельную связь один-к-одному с `Product`) с автором,
  издательством, годом, языком, переплётом, ISBN-13 и числом страниц. ISBN хранить строкой, учитывать
  издания без ISBN и прежние товары. Поля, поиск и фильтры делать явной частью API. Как минимум
  фильтровать по переплёту и искать по кириллическим названию и автору без учёта регистра.
- Остатки и цены издания и его складских вариантов принадлежат существующим моделям. Разные
  издания с разными ISBN — отдельные карточки. Сохранить старую семантику варианта по умолчанию,
  возврата остатков и снимков заказов. Категории книг образуют дерево жанров.
- Бизнес-правило домена для согласования — **до 5 экземпляров одного издания на заказ**. Суммировать
  строки по товару, в том числе при разных вариантах. Проверять в `place_order` до списания остатков
  в той же транзакции. В корзине и оформлении объяснять лимит до отправки. Проверка остатков
  самостоятельная. Превышение даёт понятный 400, корзина, заказы, остатки и счётчик промокода сохраняют
  прежнее состояние. Граница 5 должна проходить при достаточном остатке.
- Воспроизводимый `seed_demo` загружает минимум 20 книжных изданий, жанры и сотрудников с покупателями.
  Использовать стабильные идентификаторы, файлы демоизданий и повторяемый импорт. Повторный запуск
  сохраняет уже выданные пароли, управляемые сотрудником цены/остатки и фото. Для старой базы
  предусмотреть отдельный явный режим архивации известных учебных позиций по идентификаторам
  старых наборов. Проверять список перед записью, сохранять ссылки из заказов и чужие данные.
  Чистый запуск должен сразу показывать только книжные данные.

### Персонал, модули и границы доверия

- Отдельный ленивый каркас `/manager` с навигацией, ошибками и защищёнными вложенными страницами
  заказов, каталога, создания/редактирования книги, отзывов, промокодов и отчётов. Операции персонала разместить под
  `/api/manager/`. Сохранить существующие совместимые адреса заказов и использовать тот же сервис
  смены статуса. Согласовать `me.is_manager`, проверки React, модельные разрешения и класс прав DRF.
  Скрытие кнопки — удобство интерфейса. API проверяет полномочия и объекты при каждом запросе.
- Каталог персонала поддерживает поиск, страницы, черновики, создание, правку, публикацию/снятие с
  продажи и загрузку фото. Использовать `FormData`, границу multipart выставляет браузер. Проверять
  тип, декодируемость и размер изображения на сервере. Предпросмотр должен освобождать object URL.
  Изменение карточки инвалидирует кэш витрины. Управление повседневными заказами, остатками и
  модерацией доступно в SPA. Отчёт в кабинете реализовать по М4.
- М1. Писать отзыв может покупатель с доставленным собственным заказом на издание, один отзыв
  на пару покупатель–книга. Проверять доступ общим серверным правилом для `can_review` и POST.
  Новый отзыв ожидает модерации, одобренные видны в публичном списке и рейтинге, отклонённые
  сохраняются для аудита. При миграции сохранить смысл существующих `is_published`. Публичный
  список постраничный с кнопкой «Показать ещё», форма использует доступные клавиатуре звёзды.
  Сотрудник одобряет/отклоняет из очереди React, строка сразу уходит из очереди, кэш списка и
  рейтинга обновляется. Учесть конкурентный дубль и защитить от обхода через старую форму Django.
- М2. Переиспользовать модель промокода и серверную скидку. Добавить минимальную сумму корзины,
  проверку через `POST /api/promo/check/` с кодом и суммой, результат со скидкой или объяснением
  отказа. Гостевой расчёт предварительный, для корзины вошедшего источник суммы — БД. Сохранять
  код вместе с корзиной гостя и покупателя, переносить при входе по описанному правилу, позволять
  снять код. При изменениях показывать новую скидку или причину неприменимости, например
  уменьшение суммы ниже порога. При оформлении заново проверить итог по серверным ценам,
  порог, срок, активность и лимит использований в одной транзакции с блокировкой. Проверка
  кода не расходует лимит. Сохранить совместимость с текущим полем `promo_code` в checkout.
  Сотрудник видит список и число использований, создаёт и деактивирует коды в React.
- М3. Использовать действующее API избранного в сетке и карточке книги. Отметка меняется
  сразу и откатывается с сообщением при ошибке, личный кэш очищается при смене сеанса.
  Дать покупателю подписку на отсутствующую книгу и личные уведомления о её поступлении
  с действием «Прочитать всё». Счётчик в шапке обновляется каждые 30 секунд через эффект с
  очисткой таймера и при возврате на вкладку через `visibilitychange`. Сохранить существующую
  email-подписку. Привязывать личную подписку к пользователю, не выводить доступ из совпадения
  email. При пополнении из React общий сервис остатков регистрирует переход с 0 на положительный
  остаток для товара с учётом вариантов. Уведомлять подписанных один раз за цикл, включая
  повторные и конкурентные запросы. Не показывать уведомления о незакоммиченном изменении.
  Проверить переход отдельным API-тестом, а также доступ только к своим уведомлениям.
- М4. Переиспользовать `sales_report` и серверную выгрузку CSV. У сотрудника в React период по
  умолчанию последние 30 календарных дней, обе даты хранятся в URL. Показать график выручки
  по дням и диаграмму количества по статусам на Recharts или аналоге, таблицу топ-10 с
  сортировкой по столбцам на клиенте. Описать используемое определение выручки и топа.
  CSV строится за тот же период и скачивается через общий клиент с Bearer и Blob. Проверять
  диапазон дат и разрешения на JSON и CSV, сохранять защиту экранирования ячеек.
- Для входа, выхода и смены пользователя очищать персонализированные запросы, включая отзывные
  права и данные кабинета. `can_review` зависит от пользователя, поэтому не отдавать его из
  общего кэша. Для личных ресурсов проверять владельца. Ожидания при проверке — 401 без входа,
  403 при недостаточной роли, 404 при обращении к чужому заказу, 400 с объяснением при неверных
  данных или переходе. Разрешить CORS через `django-cors-headers` только явно перечисленным
  dev-источникам. Для сессии SPA стандартный путь — прокси Vite в dev и тот же origin на стенде.
- Р9. Передавать владельцу заказы в реальном времени через аутентифицированный SSE-поток. При
  подключении проверять владельца до открытия потока, передавать Bearer через общий клиент,
  не помещать токены в URL. Публиковать после коммита через общий брокер между процессами.
  При переподключении сверять актуальное состояние из БД. Закрывать соединение на выходе и
  при уходе со страницы, поддержать отзыв/истечение доступа. Настроить ASGI-обслуживание и
  проксирование потока без буферизации, сохранить обычный запуск и проверить на nginx. Таймер
  допускается для поддержания соединения и повторного подключения. Статусы поступают по событиям.
- При чтении и изменениях использовать общий TanStack Query, включая loader и action, один набор
  ключей и адресную инвалидацию. Для Р3 основные формы входа, регистрации, оформления и
  редактирования каталога используют route actions с сохранением Zod, ошибок полей, токена
  и блокировки повторной отправки. Для Ф3 дать контексты
  сеансу и корзине поверх существующих источников данных и два самостоятельных хука (например,
  задержка для фильтра и заголовок вкладки). Источник данных не дублировать.
- Для Р12 сохранить серверную пагинацию и `page` в адресе. В React загружать следующую страницу
  через IntersectionObserver с доступной кнопкой «Показать ещё». Восстанавливать фильтры, диапазон
  страниц и позицию при возврате из карточки. Прямая ссылка с `page=2` должна открыть страницу 2
  с теми же фильтрами. Использовать стабильный порядок с уникальным последним ключом сортировки
  и отмену устаревших запросов.

## Дизайн-концепция «Книжная полка»

[Открыть макет главной и карточки](docs/bookshop-design-concept.png). В макете показаны композиция и
визуальный характер. Обложки, названия изданий в подборке и цены на макете иллюстративные.

- Редакционная витрина независимого книжного. Светлые токены — бумага `#F8F4EB`, чернила
  `#24201D`, винный акцент `#472338`. Тёмные — фон `#191517`, поверхность `#261F23`, текст
  `#F5EDE5`, акцент `#E7AAC6`. Проверять пары текст/фон, включая подсказки, ссылки и кнопки.
- Выразительная антиква с кириллицей для заголовков, спокойный гротеск для навигации и форм.
  Использовать ограниченное число начертаний, локальные лицензированные шрифты и системные
  запасные. Вертикальный ритм 8/16/24/32/48 px. Контент ограничен примерно 1200 px.
- Главная. Компактная шапка, короткий редакционный заголовок «Книги, к которым возвращаются»,
  кнопка перехода к каталогу, фотография книг и блок «Выбор редакции». Каталог с быстрым поиском,
  жанрами и заметными применёнными фильтрами. Обложки с зарезервированной областью 2:3,
  `object-fit: contain`, без обрезки названия. Под обложкой идут автор, название, цена, наличие
  и понятное действие. Стабильная сетка и скелетоны одинаковых размеров.
- Карточка. Обложка и галерея, заголовок, автор, цена, наличие и действие на первом экране
  по возможности. Ниже аннотация, характеристики издания, отзывы и рейтинг. На телефоне
  один столбец. На ширине 360 px доступны поиск, фильтры, формы, оформление и кабинет.
- Корзина и оформление. На широком экране список и отдельная сводка заказа, на телефоне
  вертикальный порядок. Читаемые итог и условия, крупные поля с `label`, ошибки рядом с полем,
  клавиатурный фокус, единые состояния загрузки, отказа и пустого списка.
- Кабинет сотрудника. Самостоятельный рабочий каркас с компактной навигацией и приоритетом
  читаемости. Заказы и каталог в таблицах на широком экране, карточки строк на телефоне.
  Статусы различаются текстом, опасные действия требуют осмысленного подтверждения, диалоги
  возвращают фокус. Предусмотреть тему, размеры и состояния для обеих частей SPA.
- Для товаров использовать реальные фото или цифровые изображения обложек именно продаваемых
  изданий. Хранить проверяемое происхождение и разрешение на распространение. Подойдут
  собственные фото или изображения с подходящими условиями использования. Перепроверять ISBN,
  связь файла с книгой и доступность на чистой установке без обращения к сайтам-источникам.
  Демоассеты отделить от пользовательских загрузок. Сжимать и задавать размеры изображений.
  Для фотографий товаров использовать проверенные изображения изданий. Макет задаёт визуальный ориентир.

## Приёмка и изменения документации

- После каждого шага проверять изменённый сценарий в dev, для релизных изменений также в HTTPS.
  Проверять миграции на чистой базе и на копии данных исходного проекта. Не удалять рабочие тома.
- В финале `README.md` содержит описание, роли, 8–12 сценариев, воспроизводимый пошаговый запуск,
  демодоступы, все рабочие адреса API с методами и доступом, 3–4 примера JSON, правила домена,
  модулей и merge, краткий реестр М1–М4 и Р1–Р14, автоматические проверки и ручную приёмку по части 7.
  Историю лабораторных, развёрнутые замеры и старые отчёты хранить в профильных документах.
- Автоматический минимум — Django `check`, `makemigrations --check --dry-run`, тесты (≥15
  осмысленных API-тестов на `APITestCase`), OpenAPI без предупреждений, lint/typecheck/build/test фронтенда,
  Playwright и CI. Негативные проверки описать отдельно с подготовкой данных, точным действием
  или запросом, ожидаемым кодом и состоянием после отказа.
- Финиш — запуск по README из чистого клона до 15 минут, два сквозных сценария и негативные
  проверки, зачётные артефакты доступности, зелёный CI и тег `v2.0` на принятом коммите. Вести
  историю по КТ1–КТ4, запланировать не менее 25 содержательных коммитов, приглашение преподавателю
  владелец отправляет сам. Владелец должен уметь объяснить ключевые места и показать маленькое
  изменение на защите.
