# Лабораторная №10. Проверка самостоятельных заданий

## Состав сборки

В PowerShell выполните `$env:ANALYZE='1'; npm --prefix frontend run build`, затем откройте
`frontend/dist/stats.html`. Уберите переменную командой `Remove-Item Env:ANALYZE`.

В текущем основном файле крупнейшие модули по данным визуализатора: React DOM client
(529 536 байт), QueryObserver TanStack Query (13 069 байт) и scheduler React (9 044 байта).
Визуализатор показывает размеры модулей до итогового сжатия. Модули React DOM и scheduler
нужны при первом отображении. QueryObserver используется каталогом и навигацией. Для
дальнейшего уменьшения начальной загрузки можно исследовать загрузку страниц каталога и
деталей по требованию, измерив влияние дополнительных запросов на переходы.

## Предзагрузка

В DevTools откройте Network, выберите замедленную сеть и обновите каталог. Наведите курсор
на «Войти» и найдите запрос LoginPage. Добавьте товар в корзину, откройте её и наведите
курсор на «Оформить заказ». В списке запросов появится CheckoutPage до нажатия.

## nginx и настройки

Запустите стенд из этой ветки, задав отдельный APP_VERSION, и выполните
`docker compose -f docker-compose.prod.yml --env-file .env.prod ps`.
Сервис nginx должен получить состояние healthy. Проверка обращается к `/healthz/` через HTTPS.

Параметр `SUPPORT_PHONE` задаётся при запуске nginx. В подвале отображается его значение.
Проверьте `curl.exe -kI https://localhost/config.js`: ответ должен содержать `Cache-Control: no-store`.
Измените значение переменной и пересоздайте контейнер nginx с тем же образом, чтобы проверить
новый телефон без пересборки. Допускаются цифры, пробел, плюс, скобки и дефис.

## Результаты проверки

Исходный замер лабораторной: основной файл 505,12 КБ (156,53 КБ gzip). После разбиения
основной файл текущей сборки — 257,26 КБ (80,37 КБ gzip); это сравнение размера основного
файла, а не всего трафика при открытии каталога.

Отчёты Lighthouse 13.6.0 для HTTPS-стенда с мобильной конфигурацией находятся в
`docs/lighthouse/home.json` и `docs/lighthouse/product.json`. Главная: Performance 98,
Accessibility 100; `/products/bk-001`: Performance 95, Accessibility 100. Оценка
производительности зависит от нагрузки компьютера и содержимого каталога.
На мобильном экране область категорий получила фиксированную высоту с прокруткой:
это устранило сдвиг каталога при загрузке списка категорий.

Проверено: `+7 123 456-78-90` и значение по умолчанию отдаются в `/config.js` при
последовательном пересоздании nginx без сборки. Проверка здоровья использует IPv4
`127.0.0.1` и заголовок `Host: localhost`: иначе wget может выбрать IPv6, где nginx не слушает.
Проверочный сервис запускается после `nginx: service_healthy`:

```powershell
docker compose -f docker-compose.prod.yml --env-file .env.prod --profile checks up -d site-check
docker compose -f docker-compose.prod.yml --env-file .env.prod ps -a site-check
```

Ожидается `Exited (0)`. Для изменений из этой ветки задайте в `.env.prod` отдельную
метку образов, например `APP_VERSION=1.2.1-lab10`, и сначала соберите их через
`docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build`.

## Сверка с частью 13

В репозитории присутствуют ленивые маршруты, jitless Zod, многоэтапный Dockerfile,
SPA fallback, настройки кэша и заголовков, версия и тег v1.2.0. На стенде прошли пять
HTTPS e2e-сценариев, 152 теста Django и 44 теста фронтенда; проверены типы и линтер.
Проверка здоровья nginx и настройки телефона проверены на работающем контейнере.
Ревью части 10 сохранено в `docs/lab10-config-review.md`. Откат 1.2.0 → 1.1.0 → 1.2.0
проверен с compose-файлами соответствующих тегов и ответами `/healthz/`; в 1.1.0
вернулась серверная витрина. Из compose 1.2.0 одна смена `APP_VERSION` потребовала бы
отсутствующий образ `shop-nginx:1.1.0`.

Hotfix выпущен через PR #45 в main и PR #46 обратно в develop, создан аннотированный
тег `v1.2.1`. На образах из чистых исходников проверены 1.2.1 → 1.2.0 → 1.2.1,
версии API и подвала, а также порядок кнопок менеджера в браузере.

Предзагрузка проверяется автоматическим HTTPS-тестом с ограничением сети. Проверка
консоли охватывает каталог, товар, корзину, вход, регистрацию, оформление, заказы и
раздел менеджера; ошибки JavaScript и сообщения консоли в этом сценарии отсутствуют.
Для гостя восстановление отсутствующей сессии возвращает 204; неверный refresh-токен
по-прежнему возвращает 401. Это убирает ненужную ошибку в консоли гостя.
