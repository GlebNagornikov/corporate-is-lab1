# Лабораторная №9. Проверка самостоятельных заданий

Запустите проект командой `docker compose up -d`. Откройте витрину на
`http://127.0.0.1:5173` и админку разработки на `http://127.0.0.1:8000/admin/`.
Для cookie используйте один и тот же адрес витрины на протяжении проверки.

1. **Отзыв.** Войдите покупателем и откройте товар, на который этот покупатель ещё не
   оставлял отзыв. Клавишей Tab перейдите к звёздам, стрелками выберите оценку, введите
   текст и отправьте. Новый отзыв и рейтинг появятся без перезагрузки. Повторите
   отправку для того же товара и проверьте сообщение над формой.
2. **Пагинация.** В «Моих заказах» покупателя и «Заказах магазина» менеджера нажмите
   «Следующая». Для появления ссылки в списке должно быть больше 20 заказов, а в
   панели менеджера этот порог относится к выбранному фильтру. Проверьте `?page=2`,
   обновите страницу и вернитесь назад. У менеджера параметр `status` сохраняется
   при переходе между страницами. С замедленной сетью прежние строки видны до
   загрузки новых.
3. **Действия менеджера.** У заказа с доступной отменой нажмите «Отменить». Фокус
   должен перейти в поле причины, а Escape должен закрыть окно и вернуть фокус
   на кнопку. Откройте окно снова, убедитесь, что пустая причина блокирует
   подтверждение, затем заполните её и отправьте. Причина появится в истории
   заказа. Серверную проверку пустого комментария можно прогнать отдельно:

   ```powershell
   docker compose exec web python manage.py test orders.tests.test_api.OrderApiTests.test_manager_cancellation_requires_a_comment --settings=config.settings.test
   ```

4. **Изменение цены.** Выйдите из витрины, добавьте в гостевую корзину обычный
   товар без вариантов и запомните цену. В админке разработки временно измените
   его цену. Войдите в витрину покупателем и откройте корзину. Проверьте сообщение
   «Цена изменилась: было …, стало …» и новую цену строки. После проверки верните
   исходную цену в админке.
5. **Cookie-сессия.** Войдите в витрину. В DevTools откройте Application → Cookies
   и проверьте у `shop_refresh` флаги `HttpOnly`, `Secure`, `SameSite=Strict`
   и путь `/api/auth/`. В Local Storage ключей `shop-access` и `shop-refresh`
   быть не должно. Обновите защищённую страницу и в Network проверьте успешный
   `POST /api/auth/session/refresh/`. В консоли выполните запрос без CSRF-заголовка:

   ```js
   fetch('/api/auth/session/refresh/', { method: 'POST' }).then((r) => r.status)
   ```

   Ожидается `403`. Затем нажмите «Выйти» и проверьте, что cookie удалена,
   а открытие защищённого маршрута ведёт на вход с параметром `next`.

`HttpOnly` запрещает JavaScript читать refresh-токен. `Secure` предназначен для
защищённого транспорта, `SameSite=Strict` ограничивает межсайтовую отправку, а
`Path` сужает список получателей cookie. Access-токен живёт в памяти вкладки и
выдаётся заново при обновлении страницы. При XSS вредоносный скрипт всё ещё может
выполнять запросы в уже открытой сессии, поэтому защиту от XSS нужно сохранять.

Браузер прикладывает cookie автоматически, поэтому refresh, вход и выход
проверяют CSRF-токен и источник запроса. Для обычных операций SPA передаёт
access-токен явно в заголовке Authorization.

## Автоматические проверки

```powershell
npm --prefix frontend run typecheck
npm --prefix frontend run lint
npm --prefix frontend test
npm --prefix frontend run e2e
docker compose exec web python manage.py spectacular --validate --fail-on-warn --file /tmp/lab9-schema.yaml
docker compose exec web python manage.py test --settings=config.settings.test
```
